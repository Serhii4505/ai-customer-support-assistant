## Что готово и проверено

- Python API на FastAPI принимает сообщения и сохраняет их в SQLite.
- Помощник отвечает по FAQ, распознаёт просьбу о менеджере и направляет неизвестные вопросы в очередь.
- Пустые сообщения отклоняются; пустые имя и контакт преобразуются в null.
- Приветствия и благодарности не создают запрос менеджеру.
- Имя и контакт сохраняются между сообщениями по conversation_id. Разные разговоры не смешиваются.
- Первый содержательный запрос сохраняется по простым правилам и используется в ответе при обращении к менеджеру.
- Для разговора с conversation_id создаётся одна заявка; её контакт можно обновить.
- Очередь и отдельный запрос менеджеру показывают исходную задачу и актуальный контакт, даже если контакт появился позже.
- Запрос можно отметить обработанным: статус completed, исключение из очереди pending.
- Все таблицы создаются при запуске. Соединения SQLite закрываются после операций.
- Проверка на временной базе прошла, включая сохранение данных и удаление файла после закрытия соединений.
- В n8n проверена цепочка Webhook → HTTP Request → If → Respond to Webhook. Обе ветки возвращают ответ клиенту.
- История сообщений связана с `conversation_id`.
- Каждое сообщение сохраняется вместе с идентификатором разговора.
- Добавлен endpoint `GET /conversations/{conversation_id}/messages`.
- Проверено: один разговор корректно возвращает сообщения по порядку.
- История диалога хранится по `conversation_id` с ролями `user` и `assistant`.
- AI-клиент подключён через OpenAI API, при недоступности API используется fallback на локальную rule-based логику.
- Из текста клиента автоматически извлекаются имя, email/телефон и исходная задача.
- Реализован lead scoring: `cold`, `warm`, `hot`.
- `lead_score` сохраняется в SQLite и доступен через API.
- В n8n добавлена ветка `Hot Lead?`.
- Для `hot`-лидов автоматически отправляется Gmail-уведомление менеджеру.
- Gmail OAuth подключён и протестирован.

## API

- GET /health — проверка сервера.
- POST /chat — сообщение, необязательные name, contact, conversation_id.
- GET /leads/{lead_id} — заявка.
- GET /handoffs — очередь ожидающих запросов.
- GET /handoffs/{handoff_id} — отдельный запрос менеджеру.
- POST /handoffs/{handoff_id}/complete — отметить обработанным.
- `GET /conversations/{conversation_id}/messages` — возвращает историю сообщений конкретного разговора.

## Известные ограничения

- Полная история сообщений пока не связана с conversation_id.
- Исходный запрос определяется простыми правилами; автоматическое уточнение или смена задачи не реализованы.
- Старые заявки и разговоры не были полностью перенесены на новую схему связей.
- У запроса, созданного до заявки, lead_id может оставаться null, хотя имя и контакт уже видны через conversation_id.
- Каждое новое обращение к менеджеру может создать отдельный handoff.
- Записи сообщения, заявки, handoff и памяти выполняются отдельными транзакциями.
- Контроль доступа отсутствует: это локальный учебный прототип.
